----------- Планирование API библиотеки
- Требования к API
 - Парсер должен быть написан с использованием крейта chumsky
 - Парсер должен иметь свой API соответсвующий функционалу
 - Парсер должен использовать уже готовый лексер из lib_rottl/lexer.rs
 - Парсер должен использовать грамматики в нотации EBNF из файла docs/ebnf/OTTL.ebnf
 - Парсер должен для анализа входной строки принимать:
  - Входную строку
  - Map из имен функций (editors, converters) в виде строк и callbacks функций для обработки вызовов сделанных AST моделью, которую в свою очередь должен сгенерировать парсер
  - Map из значений ENUM и соответсвующих им числовых значений 
  - Функцию для трансляции пути (PATH) в коллбэк функцию
  - Каждая коллбак функция принимает на вход пользовательский контекст (некий объект который будет определен позднее, пока просто заглушка) и список аргументов.
    Каждый аргумент может быть 
      - bool (BOOL_LITERAL)
      - int64 (INT_LITERAL)
      - float64 (FLOAT_LITERAL)
      - string (STRING_LITERAL)
      - функция (EDITOR_INVOCATION, CONVERTER_INVOCATION)
      - путь (PATH), 
      - булево выражение (BOOLEAN_EXPRESSION)
      - математическое выражение (MATH_EXPRESSION)
      - список (LIST)
      - карта (MAP)
 - Парсер на выходе должен вернуть объект который принимает на вход пользовательский контекст  (некий объект который будет определен позднее, пока просто заглушка)
 и возвращает либо ошибку либо код успешного выполнения

Пожалуйста сгенерируй API соответствующие этим требованиям и помести его в файл src/lib_rottl/parser.rs
Исли что-то из описанного выше тебе не ясно или вызывает сомнения - сначала спроси и только получив все уточняющие вопросы - сгенерируй API

----------- Интеграция парсера
Теперь, когда публичные API для библиотеки готовы, лексер написан, EBNF грамматика для языка OTTL описана я хотел бы приступить к интеграции парсера и AST.
Для этого тебе потребуется
 - лексер из файла lexer.rs и все его лексемы
 - публичное API из файла mod.rs, значения, API парсера, callbacks, maps и тд
 - публичное API не должно подвергаться изменениям
 - Любые другие изменения в файлах кроме parser.rs должны быть сделаны только с предварительного разрешения пользователя, желательно обойтись без них
 - файл docs/ebnf/OTTL.ebnf с формальным описанием грамматики для языка OTTL
 - файл parser.rs где должна быть имплементирована реализация парсера, AST и логика эвалюации выражения по дереву AST
Пожалуйста используя крейт chumsky создай имплементацию парсера в файле parser.rs:
 - Функция Parser::new должна создать парсер, по правилам грамматики EBNF
 - Функция Parser::new должна прекратить свое выполнение при ошибках, сохранить их и вернуть в фунции is_error
 - Функция Parser::new должна на основании EBNF правил и входящего параметра _expression создать AST представление 
 - Функция Parser::new должна добавить в AST на основании editors_map ссылки на колбаки в соответсвии с именами editors функций из выражения
 - Функция Parser::new должна добавить в AST на основании converters_map ссылки на колбаки в соответсвии с именами converters функций из выражения
 - Функция Parser::new должна добавить заменить все enums в AST на их чесленное представление в соответсвии с enums_map
 - Функция Parser::execute при эвалюации (обходе и вычислении) AST должна использовать path_resolver_cb (предоставленный в Parser::new) для чтения или записи путей
 - Функция Parser::execute при эвалюации должна прервать свое выполнение и вернуть ошибку если таковая была найдена или возращена вызываемыеми методами
 - Функция Parser::execute должна вернуть Nil значение если выражение и AST не возвращают значения, в противном случае вернуть значение выражения
 - Если для выполнения этого запроса тебе нужна дополнительная информация - спроси
